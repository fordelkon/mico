# Design Principles

Use these rules when designing, changing, or reviewing module boundaries. Tests verify today's behavior; they cannot answer whether this change made the next change harder. Watch the complexity of interactions between modules: how much detail of other modules a change must know, and how many cross-module conventions it must maintain. This document owns the repository's process and module boundaries and how to judge and review them.

## Architecture and Ownership

Mico follows Electron's three-process model. Keep domain state with its owner and communicate across processes only through the typed IPC surface.

- `src/renderer/`: browser-only React product UI; consumes `window.api` and shared types, never Electron or Node APIs directly.
- `src/preload/`: security boundary; exposes typed, task-focused capabilities and hides Electron transport details.
- `src/main/`: native resources, application lifecycle, persistence, and service composition. IPC validates untrusted renderer input before delegating to the owning service.
- `src/shared/`: environment-neutral domain schemas, IPC request/response schemas, and channel names; no browser, Node, or Electron dependencies.
- `packages/ui/`: reusable UI primitives and composites. Keep product-specific compositions in the renderer.
- `packages/coding-agent/` owns coding sessions, tool execution, skills, prompts, context preparation and compaction policy. Its environment-neutral `/contracts` entry supplies shared data schemas.
- `packages/agent-core/` runs model and tool steps, owns bounded text execution and retry policy, and reports execution facts to the host.
- `packages/ai-providers/`: provider adapters, protocol parsers, normalized stream parts, and model thinking-capability mappings. Keep application configuration and service composition in main.

Fix limitations at the owning module rather than compensating in consumers. Proceed with root-cause fixes within scope; discuss changes that exceed the authorized contract or require restructuring the architecture.

### Imports and Infrastructure

- Use relative imports for siblings and private details within a feature or domain.
- Use process-root aliases only for stable cross-domain imports: `@main/*`, `@renderer/*`, and `@shared/*`. Add aliases only for established boundaries with multiple consumers.
- Consume workspace packages through their public APIs. Use the package roots for execution and `@mico/coding-agent/contracts` for environment-neutral data shared with preload or the renderer.
- Keep aliases consistent across affected Electron-Vite and TypeScript configurations. Keep build, type-check, and lint configuration process-aware and separate from application-domain code.
- Prefer `@electron-toolkit/*` utilities and established library features over custom infrastructure.

## Ask Whether the Interface Isolates Change

- When a module's internals change, its outside interface should rarely need to. Use git history to compare interface changes against implementation changes for each module.
- An interface change is not itself a problem when the business changed. The smell is an internal-only change dragging callers along: volatile internals leaked through the interface, or the responsibility and boundary need adjusting.
- When the ratio stays high, re-abstract, redesign the interface, or merge the modules.

## Enforce Boundaries with Mechanisms, Not Vigilance

- A boundary that relies on people remembering it is nominal. For each convention, measure how many of the places that could violate it are covered by an enforced check — raise that coverage, not the count of violations caught.
- Prefer the compiler, lint, and tests as enforcement. This repo enforces: the typed IPC surface as the only cross-process path, the public root as the only entry to `@mico/ai-providers`, and recurring anti-patterns through the [anti-slop rules](../tools/oxlint/anti-slop).
- When a concept gets a name, a request path, or a cancellation mechanism, allow exactly one of it. What cannot be enforced mechanically belongs on the review checklist below.
- The `architecture/process-imports` rule in [the ESLint plugin](../scripts/lint/architecture.mjs) checks process, package, and AI module ownership for imports, re-exports, dynamic imports, and `require`. It resolves named workspace imports against package exports and checks ownership for relative paths and process aliases. The coding-agent package uses agent-core and provider interfaces. Desktop storage and approvals implement the host interfaces. Renderer, preload, and shared code consume coding-agent data through its contracts entry. That entry can run without Node or Electron. Core has no application dependencies.

## Keep Shared Modules Free of Special Cases

- A parameter serving only one or two callers is a question, not a verdict — good defaults also keep parameters unused. The smell is each new consumer requiring its own parameter and branch combination.
- When callers must combine flags carefully ("A needs this, B must not enable that"), the special logic belongs in the specific business or in a narrower interface, not in the shared module.

## Review What Is Expensive to Reverse

- Coupling and change-coupling metrics give hints; the question behind them is whether the cost of common changes keeps rising.
- Spend human review on decisions that are hard to reverse once wrong — ownership boundaries, interface shapes, abstraction seams — not on every line. Let the three checks above surface the evidence worth reviewing.

## Main AI Modules

The [coding agent](../packages/coding-agent/README.md) runs a coding session from turn admission through streamed output, tool execution and settlement. It coordinates model profiles, title requests, cancellation, manual and automatic compaction, and shutdown. Its host supplies model selection, approvals, and durable session operations. Turn events are delivered to a caller-supplied listener.

- `conversation` selects and pins the execution profile, captures turn sources, runs the model loop, projects output, and coordinates checkpoints. Synchronous journal acknowledgements keep model intent durable before tool dispatch and settlement durable before display.
- `context` builds provider requests. Admission and execution measure the same projected messages and tool schemas. Tool history budgets apply to prepared requests. Summary planning preserves ordered text and tool evidence, splitting oversized parts with source positions. Each request includes fixed instructions and the provisional checkpoint within a 32,000-token estimated input budget and a 1 MiB UTF-8 resource ceiling; the source has an 8 MiB ceiling.
- `prompt`, `skills`, and workspace source preparation own harness instructions, discovery, constrained skill reads, and project guidance. Remembered preferences and project instructions remain attributed to their original source.
- `tools` owns the workspace tool set, authorization policy, execution hooks, and target revalidation. The host receives approval requests and returns decisions.
- The [agent core](../packages/agent-core/README.md) runs model steps, bounded text requests, and retry policy. Title generation and compaction retain separate drain and persistence policies.

Under `src/main/ai`, the desktop host owns the SQLite session runtime and event journal, model library, registered project roots, and atomic memory storage. It also owns pending approvals and validates the responding window. Main IPC validates senders and delivers events. Shutdown stops compaction before saving renderer drafts, then drains turns and compaction before storage closes.

## Renderer Chat Modules

The renderer chat runtime is consumed through `src/renderer/src/hooks/chat/index.ts`. Its workspace interface exposes navigation, request selections, response control, and compaction state. Lifecycle flags, mutable session records, SDK `Chat` instances, and transport cancellation coordination remain internal. Transcript consumers use `useConversationTranscript` with an opaque source; approval and message-list subscriptions retain their independent update cadence. The architecture lint rule rejects private runtime imports and SDK subscriptions outside their owning module, with transport protocol tests retaining their internal SDK seam.

Composer draft ownership is local to `components/chat/composer/draft`. The draft owner captures the submitted key and content before asynchronous work and owns acceptance, failure retention, and sending state. Its editor owns metadata-before-edit ordering and rollback when a native edit is refused; text observation reconciles labels without taking ownership of browser undo and redo. Menu, focus, and visual rendering remain in the composer. Built-in command identity is shared by recognition, completion, and submission without conflating their different queries.

Shared tool presentation owns environment-neutral facts used by multiple views. Renderer icons and running, completed, and disclosure projections remain with their presentation owners; trace persistence and normalization keep their existing contracts.

## Verify the Changed Contract

### Owned contracts in src

- Invoke task requests and results are defined in `src/shared/ipc/contracts.ts`. Main registration and the preload adapter use these schemas, and renderer method types are derived from them. Adding a task updates its contract and its task-specific handlers, not independent request and result declarations.
- A JSON document serializes mutations against its latest committed snapshot. The owner computes domain changes inside that operation; failed writes leave the committed state unchanged. Atomic file replacement is an internal persistence detail and does not promise power-loss durability.
- Active session activation applies only to the latest navigation intent. Selecting a registered sidebar project opens the new-chat surface with that project's workspace and preserves the shared new-chat draft; its disclosure control only changes history visibility. Selecting a saved conversation restores that conversation and its bound workspace. Request configuration comes from the sending session. Capability refresh and selection normalization belong to active session ownership, including when the composer changes models.
- First-send session creation captures the draft's project and request selections before persistence. A later navigation leaves that accepted response in the background instead of activating its session.
- Composer drafts live in renderer memory for the application run and remain isolated by conversation key. Long text pastes use visible labels with unique IDs and retain their original text in draft metadata; native browser editing owns undo and redo, while input observation re-associates restored labels. Sending and copying expand captured text, including skill arguments and their length validation. Damaged labels retain their payload and block sending until restored or removed; complete orphan labels cannot send without their original text. Accepted sends clear only the submitted draft, and failures preserve it.
- Provider library ownership includes valid field drafts and their single serialized save queue. Commit drains edits made during an in-flight save; a failed save retains the draft for retry. Incomplete field text stays in the form and does not replace valid persisted values.
- Renderer theme consumers derive appearance and preference from one complete `ThemeState`. Bootstrap and mutation results cannot replace a newer notification. Preload exposes task capabilities and platform information without a generic Electron transport bridge.
- Workspace path ownership includes lexical and canonical target identity, protected-path interpretation, and target revalidation after approval. Tool authorization decides whether approval is required; tools resolve again before accessing the filesystem.
- Skill catalogs resolve registered project IDs in main; renderer requests cannot select filesystem roots. Skills default to `user-invocable: true`, independently of `disable-model-invocation`. A user message persists at most one `data-skill-invocation` part containing the exact skill ID, display name, and arguments. Explicit loading validates that ID against the current turn snapshot and requires user invocation permission; display names never select an alternative skill. Model tools may access a skill with model invocation disabled only when its exact ID has been authorized for that request. Low-level snapshot reads preserve manual access for the owning service.
- Skill discovery preserves root ownership, canonical root containment, document containment, and resource identity checks. The root table covers the compatibility directories evidenced in reference agents: project `.agents/skills`, `.claude/skills`, `.gemini/skills`, `.cursor/skills`, `.github/skills`, and `skills`, then user `~/.agents/skills`, `~/.claude/skills`, `~/.config/agents/skills`, `~/.codex/skills`, `~/.cursor/skills`, and `~/.gemini/skills`; project roots precede user roots and registration order decides shadow precedence. Each root discovers one extra catalog-layout level under first-level directories that carry no `SKILL.md` of their own, with every descent gated by canonical containment. Rejected cross-root directory aliases omit their redundant diagnostic only when the same canonical `SKILL.md` was successfully validated through a contained root. External-only links remain rejected; canonical malformed documents and unsupported-field notices remain visible. Missing entries are skipped. Documents without frontmatter derive metadata from the directory name and first body line with a visible diagnostic; a document that opens the frontmatter delimiter without closing it is rejected. Skill names accept the compatibility pattern `^[a-z0-9][a-z0-9._-]{0,63}$`. Byte-identical documents with the same name in one scope's compatible roots use the canonical entry without a redundant shadowing notice; differing documents and project/user overrides retain source precedence and shadowing notices. Instruction documents and resource output have separate budgets owned by `packages/coding-agent/src/skills/files.ts`; model tool history preserves accepted skill instructions intact.
- Settings skill browsing includes all effective skills, including those unavailable for direct `$` invocation in the composer. Its catalog follows the active workspace, falling back to the default or first available workspace when the active workspace is unavailable. Document reads resolve an exact catalog ID in a fresh workspace snapshot and return the source and Markdown body; they do not grant invocation permission or arbitrary filesystem access.
- Tool execution accepts model intent before dispatch and persists each known settlement with per-call timestamps as it completes. Replay restores tool observations in submission order regardless of concurrent settlement order.
- Turn context preparation owns source lifetimes and request ordering. Accepted model-only context is durable and replayed once; `undefined` means unaccepted, while an empty array means accepted without extra context. Fresh project guidance remains ephemeral. Explicit skill authorization uses the exact invocation ID.
- Turn display assembly owns live chunk filtering, text limits, ordered reasoning/text/tool observations, and settled trace presentation for both completion and cancellation. Display limits do not truncate provider replay. Chunk accumulation is constant time; final projection traverses the collected observations.
- The internal session event log owns event encoding, digests, sequence allocation, context acceptance, and event projections. Session runtime owns lifecycle decisions and the transaction that combines lifecycle changes with event writes. Retrying an attempt resolves its original user message through the turn.
- Reopened renderer messages preserve exact skill invocation metadata. Conversation rename and deletion expose awaitable completion; failures retain the rename draft or restore the row and provide retry guidance.
- Provider catalog and model-selection actions reserve a serialized operation before awaiting draft saves. Remote catalog mutations reconcile authoritative models before whole-library saves; concurrent valid fields remain local. Failed reconciliation blocks stale saves until a later commit successfully retries the read.
- Model recovery retries only the current step before any provider chunk is observed, sharing a bounded turn retry budget. Automatic retries retain completed tool history and do not restart earlier model or tool steps. Context overflow returns actionable guidance without rewriting history or automatically reissuing the request. Accepted skill context retains its existing durable lifetime; system and project guidance remain ephemeral. Recovery resolves the original execution profile and blocks changed model or endpoint configuration.
- Main measures the actual prepared messages and tool definitions once per logical provider step using a versioned approximate Unicode heuristic. Independent request-scoped IPC observations update the latest ephemeral estimate for each renderer conversation without changing stream lifecycle; provider framing, hidden state and context capacity are outside this projection.
- Compaction builds from the latest checkpoint plus uncovered completed history, independently of existing runs' retry pins. It retains the most recent complete turn when an earlier uncovered prefix exists and the retained turn is at most 8,000 estimated tokens; larger turns join the summary source. Automatic admission also reserves the checkpoint's maximum projected size with all captured context, tool schemas, and the pending request before retaining that turn. Coverage ends at the summarized prefix, so retained calls and results replay together. Ordered provisional summaries remain in memory until every batch succeeds. Only normalized context overflow permits smaller-input retries, at most four across the operation, with strictly smaller requests; all attempts share a 64-request ceiling. With no new coverage, compaction is refused before dispatch. Compaction appends a source-verified checkpoint marked `manual` or `auto` at a safe, settled completed prefix; cancelled and unfinished prefixes remain excluded. Session runtime pins subsequent turns to that checkpoint and keeps retries on their original pin and execution profile. Replay projects its summary followed by paired uncovered history, clearing pre-checkpoint OpenAI Responses continuation IDs even in the retained tail while preserving signed reasoning and unrelated metadata. Responses accepted under the same pin may resume normal provider continuation. Raw events and display history remain unchanged. Failed or cancelled compaction preserves history and reports completion only after the checkpoint or notice is durable. Input estimates remain approximate and do not represent tokenizer accuracy or actual provider capacity.
- New turn admission captures workspace, skills, and remembered preferences once and measures the complete pending provider projection before writing a turn or choosing its pin. The default application input budget is 48,000 estimated tokens; `ConversationsOptions.applicationInputBudgetTokens` accepts a positive integer or `false`. Above budget, admission attempts at most one automatic compaction of a newer safe prefix, then measures again. Failure, no new safe coverage, or a still oversized request is reported before acceptance. Retries and idempotent request replays retain their original profile and pin. A new request publishes its default profile only after acceptance and only if the previously captured selection is unchanged; a model or thinking preference changed during capability lookup or admission takes precedence, and refused admission does not rewrite it. Provider overflow does not trigger an automatic replay or repeat tools. Concurrent admission, deletion, and manual compaction for the same session are rejected while work is active; cancellation is immediate and acknowledgement waits for durable settlement.
- Persistent memory lives under the application's userData memory directory, outside projects. User knowledge is shared across projects; project knowledge is bound to the registered project ID and survives project rename/archive. Only bounded user/feedback summaries are injected as ephemeral attributed context; full records are read on demand through SearchMemory. RememberMemory and ForgetMemory require approval even in acceptEdits mode, commit against the latest per-scope document with revision checks, and return receipts after persistence. Deletion retains a tombstone to block stale writes and excludes the record from future reads, without scrubbing earlier conversation history. Each scope has a single process owner; file replacement does not promise cross-process transactions or power-loss durability. Automatic model-based extraction is not enabled.
- Accepted model steps persist optional normalized provider usage alongside each response, including tool rounds and output-limit continuations. Counters must be finite and nonnegative; unavailable usage and fields remain absent, and terminal outcomes do not rewrite completed steps.
- Tool intent is durable before dispatch; each known settlement stores its complete result and trace before display or model-context truncation. Cancellation notifies the renderer immediately, then persists its stopped snapshot after in-flight tools settle. Sending and deletion wait for the matching request's durable cancellation acknowledgement; an early SDK ready state does not release that gate. Started tools without a known result block recovery.
- Native Quit waits for a bounded renderer draft-save attempt, aborts turns, and waits for a bounded execution drain before closing storage, then resumes native exit once. Timed-out execution callbacks cannot write to closed storage. Tray hiding does not trigger that drain. A settled acknowledgement is not a durability guarantee, and forced OS termination can bypass graceful shutdown.

Apply the [repository verification requirements](agent-guide.md#verification). For design changes, check the trend, not a score: external adaptations after internal changes are shrinking, boundary conventions are moving from documentation into enforced checks, and shared interfaces are not accumulating business-specific cases. Report the evidence and any gaps; no metric replaces business judgment.
